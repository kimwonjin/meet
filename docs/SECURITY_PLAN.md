# 보안 강화 계획

## 지금 상태 (왜 필요한가)
- **로그인**: 전화번호만 입력하면 로그인된다. 남의 번호를 알면 그 사람으로 들어갈 수 있다.
- **DB 접근**: 앱에 들어 있는 공개 키(anon key)로 모든 표를 읽고 쓸 수 있다 (allow-all 규칙).
  누가 요청했는지 DB가 모르기 때문에, 표마다 "내 것만" 같은 규칙을 걸 수 없다.

→ 순서가 정해져 있다: **① 본인 확인 로그인 → ② 로그인한 사람 표시(토큰) → ③ 표별 규칙 → ④ 서버 전용 표 잠금**

## 단계
| 단계 | 내용 | 외부 준비물 |
|---|---|---|
| ① 본인 확인 로그인 | 6자리 간편 비밀번호(PIN) 또는 문자 인증 | PIN: 없음 / 문자: 문자 발송 업체 가입 |
| ② 로그인 토큰 | 로그인하면 서버(Vercel)가 서명한 토큰을 주고, 앱은 모든 요청에 붙인다. DB는 토큰으로 사용자를 안다 | Vercel 환경변수에 Supabase JWT 비밀값 등록 (대표님이 직접) |
| ③ 표별 규칙 | 내 정보만 수정, 내 회원만 보기, 운영자만 정산 처리 등. 여러 사람이 얽힌 작업은 서버 함수로 옮김 | 없음 (SQL 실행) |
| ④ 서버 전용 표 잠금 | 알림 서명 키·탈퇴 번호 흔적은 앱에서 못 읽게, 발송 서버는 서버 전용 키 사용 | Vercel 환경변수에 service_role 키 등록 (대표님이 직접) |
| ⑤ 사진 보호 | 채팅 사진(`profile-photos/chat/…`)은 대화 당사자만 볼 수 있게 비공개 저장소 + 짧은 기간 열람 주소로 바꾼다. 프로필 사진도 같은 방식 검토 | 없음 (SQL·저장소 설정) |

- 비밀값은 대표님이 Vercel 화면에 직접 넣는다. 채팅이나 코드에 적지 않는다.
- 각 단계는 SQL 실행 전에도 앱이 그대로 동작하게 만든다. ③은 표 몇 개씩 나눠서 적용하고 매번 전체 테스트를 돌린다.

## 결정이 필요한 것
1. 본인 확인 방법: PIN(지금 바로, 무료) / 문자 인증(업체 가입 필요, 건당 10~20원) / PIN 먼저 + 문자 나중
2. 기존 계정: 실제 사용자가 아직 없으므로 테스트 계정은 다음 로그인 때 PIN을 만들게 한다
